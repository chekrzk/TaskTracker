# Жир

Учебное приложение для управления компаниями, продуктами, командами и задачами.
Техническое задание находится в `AGENT.md`.

## Локальный запуск в Windows PowerShell

Используемое окружение: Python 3.14, Django 5.2, SQLite.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py runserver
```

Открыть http://127.0.0.1:8000/. Активировать виртуальное окружение не требуется:
команды используют его интерпретатор напрямую.

Настройки рассчитаны на локальную разработку: `DEBUG=True`, разрешены хосты
`localhost` и `127.0.0.1`, используется ключ только для разработки.
База `db.sqlite3` создаётся командой `migrate` и не включается в Git.

## Этап 2: модели и связи

В `tracker/models.py` созданы семь моделей (с учётом настраиваемых колонок):

| Модель | Поля и назначение |
| --- | --- |
| `Company` | `name`, необязательное `description`, обязательный `owner`, даты создания и обновления. |
| `Product` | Компания `company`, название, описание, даты создания и обновления. |
| `Team` | Продукт `product`, название, описание, даты; участники `members` через `TeamMember`. |
| `TeamMember` | Команда `team`, пользователь `user`, роль `role`, дата вступления `joined_at`. |
| `BoardColumn` | Команда `team`, название `name`, порядок `position`. |
| `Task` | Команда, колонка `column`, название, описание, тип, приоритет, автор, исполнитель, даты создания/обновления и срок выполнения. |
| `Comment` | Задача, автор, обязательный текст, даты создания и обновления. |

У каждой модели автоматически создаётся числовой первичный ключ `id`.
Названия компаний, продуктов, команд и задач ограничены 255 символами.
Даты создания заполняются через `auto_now_add`, даты обновления — через
`auto_now` при обычном `save()`. Срок задачи — `DateField`, без времени.
Добавлены русские подписи моделей и полей, а также `__str__()` для читаемого
представления объектов. Комментарии сортируются по дате создания и `pk`.

### Связи

Иерархия: `Company → Product → Team → Task → Comment`.
Все ссылки на пользователей используют `settings.AUTH_USER_MODEL`;
в проекте по-прежнему используется стандартная модель Django `auth.User`.

Обратные связи доступны через:

- `user.owned_companies`, `company.products`, `product.teams`;
- `team.members` и `user.teams` — пользователи и их команды;
- `team.memberships` и `user.team_memberships` — записи членства с ролями;
- `team.columns`, `column.tasks`, `team.tasks`, `user.authored_tasks`, `user.assigned_tasks`;
- `task.comments` и `user.task_comments`.

### Значения и ограничения

- `TeamMember.Role`: `LEAD`, `DEVELOPER`, `TESTER`, `MEMBER`.
  По умолчанию — `MEMBER`.
- `Task.Type`: `TASK`, `BUG`, `STORY`. По умолчанию — `TASK`.
- `Task.column` — обязательная ссылка на колонку своей команды; фиксированного перечисления статусов нет.
- `Task.Priority`: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`.
  По умолчанию — `MEDIUM`.
- Исполнитель и срок задачи необязательны: `blank=True, null=True`.
- `UniqueConstraint(team, user)` с именем `unique_team_member` запрещает
  повторное членство на уровне базы данных. Пользователь может вступить
  в несколько разных команд.
- `Task.clean()` проверяет, что выбранный исполнитель состоит в команде
  задачи; ошибка относится к полю `assignee`. Также проверяется принадлежность
  колонки команде (ошибка `column`). Проверки учитывают и смену команды.

Перечисления оформлены через `TextChoices`. Допустимость их значений,
обязательность текстовых полей и принадлежность исполнителя проверяются
валидацией модели, а не SQL-ограничениями. При ручной записи через ORM нужно
вызвать `full_clean()` перед `save()`; `objects.create()`, `update()`
и обычный `save()` сами эту проверку не запускают. Будущие `ModelForm`
будут вызывать валидацию модели; команду задачи нужно установить до проверки формы.

### Удаление

- `CASCADE` для иерархии: удаление компании удаляет её продукты, команды,
  членства, задачи и комментарии. Пользователи сохраняются.
- `PROTECT` для владельца компании и авторов задач/комментариев:
  нельзя удалить пользователя, пока на него ссылаются эти записи.
- `SET_NULL` для исполнителя: удаление пользователя оставляет задачу
  без исполнителя, если другие связи не запрещают удаление.
- Членство удаляется вместе с командой или пользователем.

Удаление самого `TeamMember` пока не снимает назначения задач автоматически.
Обработку назначений при исключении участника нужно добавить вместе с
управлением участниками на этапе 8.

связь многие-ко-многим через `TeamMember` и ограничение уникальности.
Миграция зависит от стандартной модели пользователя и применена к локальной SQLite.

Первоначальные 13 тестов этапа 2 расширены проверками настраиваемых колонок. Проверяются иерархия и обратные связи,

команде (в том числе при смене команды), каскадное удаление, защита авторов

## Настраиваемые колонки Kanban

В `tracker/models.py` добавлена модель `BoardColumn(team, name, position)`.
Колонки сортируются по `position`, затем по `id`; одинаковые позиции допустимы.
Название можно менять, не меняя задачи, так как `Task.column` хранит ID колонки.
Поле `Task.status` и перечисление `Task.Status` удалены.

Обычное создание команды (`Team.save()` / `Team.objects.create()`) в одной
транзакции создаёт пять стартовых колонок: `TODO`, `IN PROGRESS`, `REVIEW`,
`TESTING`, `DONE`. Это шаблон начальной доски, а не ограничение допустимых
названий. Повторное сохранение команды не добавляет колонки заново.
`bulk_create()` не вызывает `save()`: для создания команд с начальной доской
использовать обычный ORM-путь.

На уровне ORM колонку задачи нужно указывать явно. В будущей форме создания
задачи будет выбрана первая колонка команды по текущему порядку; если доска пуста,
сначала нужно создать колонку. Управление колонками в интерфейсе относится к
этапу 11, перемещение карточек — к этапу 12.

`Task.clean()` запрещает колонку другой команды. `BoardColumn.clean()` запрещает
перенос колонки с задачами в другую команду. Как и остальная валидация моделей,
эти проверки требуют `full_clean()` при ручной записи через ORM.
`RESTRICT` запрещает удаление отдельной колонки с задачами, но разрешает
каскадное удаление всей команды/компании вместе с её задачами и колонками.
Пустую колонку можно удалить; перед удалением занятой нужно перенести задачи.

`tracker/migrations/0002_board_columns.py` добавляет таблицу колонок и временно
необязательный внешний ключ, создаёт колонки для существующих команд, переносит
все задачи из старых статусов, затем удаляет `status` и делает `column`
обязательным. Неизвестные старые значения сохраняются отдельными колонками.
Миграция намеренно необратима: произвольные колонки нельзя без потерь вернуть
к фиксированному перечислению. Для возврата старой схемы нужна резервная копия БД.

В `AGENT.md` обновлены сущности и схема, формы, права Team Lead, требования к
Kanban и drag & drop, MVP и этапы разработки. Новый запрос перемещения:
`POST /tasks/<id>/column/` с `column_id`; названия не служат идентификаторами.

Проверка изменения: 24 теста проходят, включая создание/переименование/перестановку
колонок, принадлежность команде, защиту от удаления занятой колонки, каскадное
удаление команды и перенос старых данных. Тест `tracker/test_migrations.py`
создаёт отдельную временную БД со старой схемой и проверяет переход на новую:
все пять прежних статусов, неизвестный статус, несколько команд и пустую команду,
сохранение задач, авторов, исполнителей, времени обновления и комментариев.

Перед применением миграции локальная SQLite скопирована в файл
`db.sqlite3-before-columns-<дата-время>`. Эта копия исключена из Git правилом
`db.sqlite3-*`. Миграция `0002_board_columns` применена; проверка
`makemigrations --check --dry-run` не обнаружила расхождений.

## Этап 3: Django Admin

В `tracker/admin.py` зарегистрированы все семь моделей:
`Company`, `Product`, `Team`, `TeamMember`, `BoardColumn`, `Task` и `Comment`.

Настройки административного интерфейса:

- Заголовок «Жир — администрирование» и главная страница «Управление данными».
- Компании: название, владелец, даты; поиск по названию, описанию и логину владельца.
- Продукты: название и компания, фильтр по компании, поиск по названию и описанию.
- Команды: название и продукт, фильтры по компании/продукту, поиск по иерархии.
- Участники: пользователь, команда, роль и дата вступления; фильтры по роли и команде.
- Колонки: ID, название, команда и порядок. Название и позицию можно редактировать
  прямо в списке; отдельная форма открывается по ID. Есть фильтр по команде.
- Задачи: ID, название, команда, колонка, тип, приоритет, исполнитель и дата создания.
  Фильтры по команде, колонке, типу и приоритету; поиск по названию, описанию,
  команде и исполнителю.
- Комментарии: ID, первые 80 символов текста, задача, автор и дата создания;
  поиск по тексту, названию задачи и автору.

Для связанных объектов подключён поиск с автодополнением. В списках используется
`list_select_related`, чтобы подгружать отображаемые связанные объекты вместе.
Для компаний, задач и комментариев доступна навигация по дате создания.
Автоматические даты и дата вступления показываются только для чтения.

`TaskAdminForm` остаётся обычной `ModelForm` и использует валидацию модели.
В выборе колонки отображается «Команда — Колонка», поскольку у разных команд
есть колонки с одинаковыми названиями. При сохранении форма проверяет, что
колонка и исполнитель принадлежат команде задачи. Повторное членство в команде
отклоняется стандартной валидацией ограничения уникальности.

В форме новой компании текущий администратор предварительно выбран владельцем;
в формах задачи и комментария — автором. Администратор может изменить этот выбор.
Создание команды через админку автоматически добавляет пять начальных колонок.
Непустую колонку нельзя удалить; админка показывает зависимые задачи.
Удаление задачи каскадно удаляет комментарии; удаление всей компании работает
вместе с зависимыми командами, колонками и задачами.

Доступ к `/admin/` использует стандартные права Django: активный пользователь
с `is_staff` и соответствующими разрешениями, либо суперпользователь.
Прикладные роли Team Lead/Developer/Tester не выдают административный доступ.
Их проверки в пользовательском интерфейсе относятся к следующим этапам.

## Этап 4: регистрация, вход и выход

Рабочая главная страница `/` теперь защищена декоратором `login_required`.
Гость получает перенаправление на `/login/?next=/`. После входа отображаются
имя пользователя и POST-форма выхода.

### Регистрация

В `tracker/forms.py` добавлена `RegisterForm` на основе стандартной
`UserCreationForm`. Форма создаёт стандартный `django.contrib.auth.models.User`
и содержит:

- имя пользователя;
- обязательный email;
- имя и фамилию;
- пароль и его подтверждение.

Пароль проходит стандартные валидаторы из `AUTH_PASSWORD_VALIDATORS` и
сохраняется штатным методом Django в виде хеша. Email приводится к нижнему
регистру и проверяется на повтор без учёта регистра. Эта уникальность
обеспечивается формой регистрации, а не ограничением таблицы стандартного
`User`; создание пользователей напрямую через ORM или Admin должно учитывать
это отдельно.

`GET /register/` показывает форму. Успешный `POST` создаёт пользователя,
сразу открывает ему сессию и перенаправляет на `/`. Уже вошедший пользователь
с `/register/` возвращается на главную страницу.

### Вход и выход

`/login/` использует стандартный `LoginView` Django и шаблон
`tracker/registration/login.html`. После входа пользователь переходит на `/`
или на безопасный локальный URL из `next`. Внешний URL в `next` игнорируется,
что предотвращает перенаправление на посторонний сайт. Уже вошедший пользователь
не видит форму входа и возвращается на главную.

`/logout/` использует стандартный `LogoutView`. Выход разрешён только POST-запросом
с CSRF-токеном; GET возвращает `405 Method Not Allowed`. После завершения сессии
пользователь переходит на `/login/`.

В `config/settings.py` заданы именованные маршруты:

```python
LOGIN_URL = 'tracker:login'
LOGIN_REDIRECT_URL = 'tracker:home'
LOGOUT_REDIRECT_URL = 'tracker:login'
```

В `tracker/urls.py` подключены маршруты `/register/`, `/login/` и `/logout/`.
Созданы отдельные шаблоны регистрации и входа. В `home.html` добавлена безопасная
POST-форма выхода. Небольшие стили полей, ошибок и кнопок добавлены в `style.css`;
общая структура страниц будет перенесена в `base.html` на этапе 5.

- отображение регистрации и CSRF-токена;
