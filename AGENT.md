# Техническое задание

## Веб-приложение управления командами и задачами Mini Jira

### 1. Цель проекта

Разработать веб-приложение на Django для управления компаниями, продуктами, командами и задачами.

Приложение должно позволять пользователям регистрироваться, входить в систему, состоять в командах, создавать задачи, назначать исполнителей, перемещать задачи между колонками и работать с Kanban-доской.

Проект разрабатывается как упрощённый аналог Jira.

Основной стек:

* Python
* Django
* Django Templates
* PostgreSQL или SQLite
* Bootstrap
* JavaScript
* SortableJS или HTML Drag & Drop API

Основной дизайн: как Jira, белые тона, минимализм. Название пусть будет "Жир"

---

## Тип задачи

Допустимые значения:

```text

```

---

## Статус задачи

Статус задачи определяется её колонкой `BoardColumn`.
Поле `Task.column` — обязательный `ForeignKey` на колонку той же команды.
Отдельного строкового поля `Task.status` и фиксированного перечисления статусов нет.
Название для отображения берётся из `task.column.name`.

`TODO`, `IN PROGRESS`, `REVIEW`, `TESTING`, `DONE` — только начальные названия.
После создания команды пользователь с правами Team Lead может создавать,
переименовывать и переставлять колонки. Логика не должна зависеть от их названий.

# 3.8 BoardColumn

Настраиваемая колонка Kanban-доски конкретной команды.

Поля:

```text
id
team
name
position
```

Связи:

```text
BoardColumn N:1 Team
BoardColumn 1:N Task
```

Правила:

* название обязательно, максимум 255 символов;
* `position` — неотрицательное целое число; порядок вывода — `position`, затем `id`;
* позиции не обязаны быть уникальными, чтобы разрешать перестановку;
* у каждой команды свой набор колонок;
* при создании команды автоматически создаются пять начальных колонок:
  `TODO`, `IN PROGRESS`, `REVIEW`, `TESTING`, `DONE` с позициями 0–4;
* начальные колонки можно переименовывать и дополнять произвольными колонками;
* новая задача получает первую колонку команды по текущему порядку;
  если колонок нет, создание задачи недоступно до добавления колонки;
* нельзя назначить задаче колонку другой команды;
* нельзя переместить колонку с задачами в другую команду;
* удаление отдельной колонки с задачами запрещено: сначала задачи нужно
  переместить в другую колонку той же команды;
* удаление команды или компании каскадно удаляет её колонки и задачи.

Проверки принадлежности выполняются при валидации моделей и в представлениях.
При прямой записи через ORM вызывать `full_clean()` перед `save()`.

# 15. Kanban board

Основная страница команды должна содержать Kanban-доску.
Колонки загружаются из `team.columns` и выводятся по `position`, затем `id`.
Задачи группируются по `Task.column_id`. Пустые колонки тоже отображаются.

Начальная доска содержит `TODO`, `IN PROGRESS`, `REVIEW`, `TESTING`, `DONE`.
Это обычные записи в БД, а не фиксированный список допустимых статусов.

Team Lead может:

* создать колонку с произвольным названием;
* переименовать существующую колонку без изменения задач;
* изменить порядок колонок с сохранением `position`;
* удалить пустую колонку.

Предусмотреть `BoardColumnForm` и маршруты:

```text
POST /teams/<team_id>/columns/create/
POST /teams/<team_id>/columns/reorder/
POST /columns/<id>/edit/
POST /columns/<id>/delete/
```

Изменение порядка принимает полный список `column_ids` команды, без повторов
и чужих ID; сервер проверяет список и записывает позиции 0..N-1 в транзакции.
Имена колонок не используются как идентификаторы.

Удаление колонки с задачами должно показывать понятную ошибку с требованием
сначала перенести задачи. На пустой доске показать возможность добавить колонку;
создание задачи при отсутствии колонок недоступно.

Каждая задача отображается карточкой. Минимальное содержимое:

```text
Task ID
title
priority
assignee
```

# 16. Drag & Drop

Пользователь должен иметь возможность перетащить задачу между колонками своей команды.
Использовать SortableJS или стандартный HTML Drag & Drop API.
Рекомендуемый вариант — SortableJS.

При переносе задачи JS определяет `task_id` и `column_id` целевой колонки.
Endpoint:

```text
POST /tasks/<id>/column/
```

Request:

```json
{
    "column_id": 12
}
```

Django должен:

1. проверить существование задачи;
2. проверить права пользователя на перемещение;
3. проверить существование колонки и её принадлежность команде задачи;
4. изменить `Task.column` и сохранить модель;
5. вернуть JSON с ID новой колонки.

Response:

```json
{
    "success": true,
    "column_id": 12
}
```

При ошибке интерфейс возвращает карточку в исходную колонку и показывает сообщение.
Названия колонок не передаются как идентификаторы.

## Этап 2. Создание моделей

Создать:

```text
Company

Product

Team

TeamMember

Task

Comment
```

Настроить связи между моделями. `Task.column` ссылается на `BoardColumn`;

## Этап 11. Kanban board

На странице команды вывести колонки из `BoardColumn` по `position`, затем `id`,
а задачи — по `Task.column`. Не задавать названия и число колонок в шаблоне.

Добавить `BoardColumnForm`, создание и переименование колонок, изменение
их порядка и удаление пустых колонок. Управление доступно только Team Lead.
Проверять права на сервере, а также принадлежность колонок команде.
Перестановку на этом этапе можно выполнить кнопками или формой.

Учесть пустую доску и запрет создания задачи, пока нет ни одной колонки.
На этом этапе без drag & drop карточек.

## Этап 12. Drag & Drop

Подключить SortableJS.

Создать:

```text
board.js
```

Добавить endpoint:

```text
POST /tasks/<id>/column/
```

При переносе карточки отправлять `column_id` и сохранять `Task.column` в БД.
Проверять права и принадлежность колонки команде задачи. При ошибке возвращать
карточку в исходную колонку.
